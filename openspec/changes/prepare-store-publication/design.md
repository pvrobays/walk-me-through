# Design

## Context

See `proposal.md` for the motivation, and the three capability specs for the required behavior. These facts about the current state shape the approach:

- **VS Code:** the VSIX is built by `npm run package:vsix` as a whitelist, through `.vscodeignore`: `dist/extension.js`, `media/`, `package.json`, and a `LICENSE` copied from the repository root. esbuild bundles markdown-it 14.3.3, linkify-it 5.0.2, mdurl 2.1.0, uc.micro 2.1.0, punycode.js 2.3.1 (all MIT) and entities 4.5.0 (BSD-2-Clause) into `dist/extension.js`. The package has no README, CHANGELOG, PNG icon or categories. That is why the live 0.1.0 Marketplace page is bare.
- **Rider:** the ZIP contains `commonmark-0.24.0`, `gson-2.13.2` and `error_prone_annotations-2.41.0` (the last is transitive through Gson, Apache-2.0), plus highlight.js 11.11.1, whose license is already a resource. `plugin.xml` has the vendor "Walk Me Through contributors" and the description "Development prototype". `build.gradle.kts` pins `sinceBuild` and `untilBuild` to `262.10968.170`, compiles against the local Rider through `RIDER_HOME`, and runs the verifier only against that Rider. The JetBrains vendor is `pvrobays`, plugin 35375; its first upload is awaiting approval.
- **Environment checks:**
  - `core/env.ts` rejects every platform except `win32` and `linux`. The publisher and VS Code use it.
  - Rider's `PlaybackEnvironment.refusal` additionally rejects any non-Windows OS.
  - The launch handlers in both IDEs check that `env.platform` equals the host's platform, using Node names; Rider maps `os.name` to those names.
- **Skill:** the bundle is installed only by `scripts/install-skill.mjs`, which compares normalized SHA-256 hashes (`hashFile`) and refuses to overwrite differing files unless `--force` is passed. `cli.ts` hard-codes `bundleVersion: '0.1.0'`, while `build.mjs` reads the bundle version from `packages/skill/package.json`.
- **Launcher:** the install targets in `packages/launcher/src/config.ts` are README anchors. A launcher test asserts that the bundle contains no URL except the repository's.

## Goals / Non-Goals

**Goals:**

- One build command per IDE produces a package that the owner can upload unchanged.
- Every new generated asset (icons, the bundled skill copy) has a single source and a check that fails when the generated copy drifts.
- Onboarding reuses the same hash and no-overwrite rules as `install-skill.mjs`, so all three installers agree.

**Non-Goals:**

- Uploading, publishing tokens, CI release jobs, or GitHub Releases.
- Detecting or upgrading an outdated skill. The offer considers only whether `SKILL.md` exists.
- Platform-specific VSIX targets. A single universal VSIX is enough now that all three desktop platforms are accepted.

## Decisions

### D1. One release version, 0.2.0, including the skill bundle

The VS Code extension, the Rider plugin and the skill bundle all move to 0.2.0. `cli.ts` gets its bundle version through an esbuild `define` from `packages/skill/package.json`, instead of a literal, so the script and manifest cannot disagree. Artifacts record `generator.bundleVersion: "0.2.0"`, which the existing semantic-version validation accepts.

*Alternative considered:* keeping the bundle at 0.1.0 until an update contract exists. Rejected: the bundle content changes (macOS wording) and now ships inside both viewers, so an unchanged version would identify two different bundles.

### D2. Icons generated by a dependency-free script

`scripts/build-icons.mjs` describes the mark once as a few primitives, based on the current activity-bar SVG (two step boxes, a connector, an arrow) on a rounded tile. It writes:

- `packages/vscode/media/icon.png` (256×256);
- `packages/rider/src/main/resources/META-INF/pluginIcon.svg` (40×40);
- `packages/rider/src/main/resources/META-INF/pluginIcon_dark.svg` (40×40).

The PNG is rasterized with 4×4 supersampling and encoded with `node:zlib` plus a CRC-32. The outputs are committed. `npm test` regenerates them in memory and compares them byte for byte. The owner reviews the result before upload.

*Alternatives considered:* `sharp` or `resvg`, rejected because they add native or WASM dependencies for a one-off asset; a hand-drawn PNG, rejected because it is not reproducible.

### D3. VS Code listing files live in the extension package

`packages/vscode/` gains:

- a Marketplace-specific `README.md` covering what the extension does, the skill install command and offer, launch links, platforms (Windows tested; Linux and macOS not verified), privacy, and a link to the repository README;
- `CHANGELOG.md`;
- `ThirdPartyNotices.txt`.

`.vscodeignore` whitelists these files, `media/icon.png` and `skill/**`. `package.json` gains `icon`, `categories: ["AI", "Education", "Other"]`, `keywords`, `homepage`, `bugs`, `galleryBanner` and `pricing: "Free"`, and keeps `private: true` so npm can never publish the package. `vsce` rewrites relative README links through `repository`, so the README uses no images.

A Vitest check reads the esbuild metafile of the extension bundle and asserts that every bundled `node_modules` package appears in `ThirdPartyNotices.txt` with its version.

### D4. Rider descriptor and build

- The description comes from `packages/rider/marketplace/description.html`, and the change notes from `packages/rider/marketplace/change-notes.html`. Both are wired into `intellijPlatform.pluginConfiguration` (`description`, `changeNotes`, `version = "0.2.0"`).
- The vendor becomes `pvrobays`, with URL `https://github.com/pvrobays`, matching the Marketplace vendor.
- `ideaVersion.sinceBuild = "262"` and `untilBuild = provider { null }`, so there is no upper bound.
- Compilation and tests stay against the local Rider 262.10968.170.
- `pluginVerification.ides` lists the local Rider and `select { types = Rider; channels = RELEASE; sinceBuild = "262" }`, which downloads the newest released Rider, possibly several GB. The verifier report records both builds.

`prepareSandbox` copies `LICENSE` and `THIRD-PARTY-NOTICES.txt` into the plugin root, so they appear at the root of the ZIP. A Kotlin unit test asserts that the notices name every jar in the sandbox `lib/` directory with its version.

*Alternative considered:* keeping the description inside `plugin.xml`. Rejected: separate HTML files are easier to review and keep the descriptor small.

### D5. Optional signing through standard variables

`intellijPlatform.signing` reads `CERTIFICATE_CHAIN`, `PRIVATE_KEY` and `PRIVATE_KEY_PASSWORD` from the environment, the convention used in JetBrains' documentation. `signPlugin` and `verifyPluginSignature` are enabled only when all three are present. Otherwise `buildPlugin` produces the unsigned ZIP as it does today. The owner generates the certificate with the documented `openssl` commands and keeps it outside the repository. `.gitignore` gains `*.pem`, `*.crt` and `*.key` under `packages/rider/`.

### D6. Platform acceptance

- `core/env.ts` accepts `darwin`. Detection of WSL, containers and SSH is unchanged, and so is the override.
- `PlaybackEnvironment.refusal` drops its OS clause and keeps the remote, headless, SSH and WSL refusals.
- All refusal messages say "local desktop" and stop saying "native Windows or Linux".
- Both launch handlers keep the exact `env.platform` match. Rider's `platformOf` already maps `Mac OS X` to `darwin`.
- Path comparison stays case-insensitive only on Windows. On macOS, Node's `realpathSync.native` and Java's `toRealPath` return the on-disk case, so canonical paths match even when a root was typed in a different case.
- `ci.yml` adds `macos-latest` to the matrix, running build, typecheck, `npm test` and `test:extension` without Xvfb. `check-workflows.mjs` asserts the three-OS matrix.
- Rider has no CI job, so Linux and macOS Rider remain fully unverified.

### D7. The skill bundle shipped inside both viewers

- **VS Code:** `build.mjs` copies the four files from `packages/skill/` to `packages/vscode/skill/` (gitignored) on every build.
- **Rider:** `processResources` copies them from `../skill` into the `skill/` resource directory.

Because the copies are made on every build, they cannot drift. Each IDE's tests still assert that the shipped files hash to the shipped `manifest.json`. On Kotlin, the hash is `SourceText.hash(SourceText.decode(bytes))`, which equals `hashFile`. The test checks it against the TypeScript manifest values.

### D8. One installer algorithm, implemented twice

The VS Code (`skill.ts`) and Rider (`SkillInstaller.kt`) installers follow the same steps:

1. Resolve the target: walk up from each candidate folder to the nearest `.git` entry (directory or file). VS Code uses the `file:` workspace folders; Rider uses `basePath` and the content roots. If no ancestor has `.git`, the folder itself is the target. Deduplicate the targets by canonical path.
2. With several targets, ask the user to choose.
3. Read each existing target file. If any differs from the bundle after normalization, write nothing and report the differing names.
4. Otherwise create the missing files exclusively (VS Code: the `wx` flag; Kotlin: `CREATE_NEW`).
5. Report one of three outcomes: installed, already installed, or refused because files differ.

The installer refuses in remote VS Code windows and in remote or headless Rider, with the local-desktop message. A shared fixture (`tests/conformance/skill-install.json`) lists the scenarios: fresh install, CRLF copy, customized `SKILL.md`, partial install, worktree `.git` file, and nested folder. Vitest drives the TypeScript logic through a Node-only helper, and Kotlin unit tests drive the Kotlin installer from the same cases.

### D9. The missing-skill offer

- **VS Code:** adds the `onStartupFinished` activation event. After activation, if `workspace.isTrusted`, the environment is accepted, and no dismissal applies, it computes the targets and shows one `showInformationMessage` with the three buttons for the first target lacking `SKILL.md`.
- **Rider:** a `postStartupActivity` (`ProjectActivity`) does the same per project, using a `Walk Me Through` notification with three `NotificationAction`s. It skips projects with no Git target.
- **Dismissal state:** both IDEs store it in application-level state only. VS Code uses `globalState`; Rider uses an application `PropertiesComponent`. The keys are `walkMeThrough.skillOffer.never` (a boolean) and `walkMeThrough.skillOffer.dismissedRoots` (canonical Git roots). Project-level storage such as Rider's `workspace.xml` would place state inside the project directory.
- **Once per session:** an in-memory set limits each root to one offer per IDE session.

*Alternative considered:* VS Code `workspaceState` for "Not for This Project". Rejected because it is keyed by workspace file rather than by repository, so the same repository opened through another `.code-workspace` would ask again.

### D10. Store targets in the launcher

`config.ts` install targets become `https://marketplace.visualstudio.com/items?itemName=pvrobays.walk-me-through` and `https://plugins.jetbrains.com/plugin/35375-walk-me-through`. The README keeps its install headings, now leading with the store link, plus a separate "Development builds" subsection for the VSIX and ZIP.

The launcher tests change:

- The URL allow-list in the static test admits exactly the repository and these two store URLs.
- The README-anchor test keeps covering the repository links that remain in the bundle and README.

The launcher help drops the "native Windows only" Rider line and states the platform status instead. A push to `main` redeploys Pages.

### D11. Manual uploads by the owner

- **VS Code:** **Update** on the extension in `marketplace.visualstudio.com/manage`, uploading `walk-me-through-0.2.0.vsix`. No token is involved.
- **JetBrains:** **Upload Update** on plugin 35375, using the signed ZIP if signing is configured, otherwise the unsigned one.

The owner then installs both packages from the stores on a clean profile for acceptance.

## Risks / Trade-offs

- **Linux and macOS behavior is untested by the maintainers.** For example, Toolbox delivery of `jetbrains://`, file-system case behavior and JCEF on macOS. → The wording says so honestly; macOS CI covers the TypeScript side; refusals still guard remote hosts; issues are handled as bugs.
- **An open-ended `untilBuild` can admit a future Rider that breaks the plugin.** → The verifier runs against the latest release before each upload, and JetBrains' own compatibility verification flags new majors. A bounded range can be reintroduced later.
- **JetBrains review may reject the description, icon, or the pending 0.1.0-prototype.** → The owner can upload 0.2.0 as an update regardless; listing text avoids prototype wording and claims only what has been verified.
- **The startup offer adds an activation and a filesystem scan to every VS Code window.** → It stats only `.git` and `SKILL.md` on the walk to the Git root, runs after startup, and does nothing in untrusted or remote windows.
- **Projects with an older or customized skill get no update prompt.** → This is intentional for now; update detection belongs to the updates change, and the README explains `npm run skill:install -- --force` for maintainers.
- **The verifier downloads several GB of Rider distributions.** → Downloads are cached in Gradle's directory; the task records the duration and size.

## Migration Plan

1. Archive `add-shared-launcher` (finishing or explicitly accepting task 7.3), then implement this change on `main`. Pushing `launcher/` changes redeploys Pages.
2. Build `npm run package:vsix` and `gradlew.bat buildPlugin` (or `signPlugin`), and have the owner upload both by hand.
3. Rollback: upload a new patch version (stores do not allow re-uploading a version). Users of 0.1.0 VSIX installs update normally. If needed, the launcher help targets can be reverted to README anchors in `config.ts` alone.

## Open Questions

- Whether JetBrains approves `0.1.0-prototype` before 0.2.0 is uploaded. This does not affect the work; the owner can upload 0.2.0 either way.
